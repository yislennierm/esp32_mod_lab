Mission

The project started as a Game Boy Color LCD bus reverse engineering effort, but it quickly became clear that the reusable result should be larger: a console picture-signal lab where the ESP32-P4 can measure pins, capture timing, test hypotheses, stream frames, and leave behind reproducible evidence.

What was being investigated

The GBC LCD flex exposes digital-looking timing and color lines plus dangerous analog LCD drive rails. The useful question was not simply "can we see a picture?" It was whether the bus could be characterized safely enough to build future tools such as screen mods, retimers, scalers, streamers, and protocol analyzers.

Why the evidence matters

Many images were wrong before they became useful. Tiled mosaics, red-only stripes, skewed frames, and odd color modes each carried information about sampling rate, byte packing, line length, sync interpretation, and electrical behavior.

Current conclusion: the GBC target is now a working reference module for a broader reverse engineering instrument. The code should keep the GBC workflow working while generic tools are extracted around profiles, captures, timing reports, and browser controls.

Timeline Of The Investigation

Phase 1

Electrical caution first

Analog LCD rails were identified and excluded from GPIO. Firmware stayed input-only while basic serial commands, pin reads, and safe command handling were brought up.

Phase 2

Timing discovery

Edge counting and timestamp captures identified frame-like and line-like candidates. The project learned that interrupt counts were useful for slow signals but not enough for the MHz-class dot clock.

Phase 3

Red data first

Red-only capture proved the data bus carried image-related structure. The output was not a frame yet, but it was no longer blind probing.

Phase 4

Red/green line bursts

Line-burst captures produced repeated mini-screens. This looked wrong at first, but it confirmed that the bus was being sampled in a consistent, image-correlated way.

Phase 5

LCD_CAM raw capture

Peripheral-backed capture produced clearer mosaics and near-readable frames. Width sweeps and host-side sliders became the fastest way to test framing hypotheses.

Phase 6

Live browser workbench

The browser view became a practical monitor and investigation surface with live frames, controls, pin/timing tools, and recovery actions.

Hardware lesson

GPIO32 was removed from the active wiring

Power-cycle failures led to discovering backfeed-like behavior. Moving CLS from GPIO32 to GPIO3 restored reliable console off/on behavior while capturing.

Safety And First Contact

The GBC LCD connector includes analog drive voltages that do not belong on ESP32-P4 GPIO. Those lines were documented as dangerous and intentionally left disconnected from the capture system.

Line group Treatment Reason
V0-V9, VCOM, VEE, VSHA, VSHD Do not connect to GPIO LCD analog/bias rails can exceed safe digital GPIO behavior.
DCLK, LP, SPL, CLS, SPS, PS Input-only timing/control candidates Useful for timing discovery when handled carefully.
R0-R5, G0-G5, B0-B5 Input-only pixel data candidates Parallel color data hypothesis.
Lesson preserved: even input-only firmware does not guarantee perfect isolation. Board-level pulls, boot strapping, leakage paths, or ESD structures can still bias an unpowered target.

Timing Discovery

Timing work started with commands that could read GPIO levels and count edges. The first useful model treated DCLK as the pixel-clock candidate, SPS as frame-like, and LP/CLS/PS as line-rate or control candidates. SPL was useful, but not safely reducible to a standard horizontal sync label.

What worked

  • Stable frame-like cadence from SPS.
  • Line-like cadence from several non-data signals.
  • Short timing captures that could be repeated and compared.

What did not prove enough

  • GPIO interrupt counting was not a valid full pixel-clock capture method.
  • Assuming VGA-style HSYNC/VSYNC/DE semantics caused misleading attempts.
  • One boot screen is not enough to prove color packing.

Representative timing evidence is preserved in the timing relationship report, the steady-state timing session, and the boot power-on timing session.

First Image Evidence

The first visual artifacts were not intended to be beautiful. Their value was in showing whether sampled bits changed in a way that correlated with display activity.

The Tiling Breakthrough

The key mental shift was accepting that the broken images were evidence. Repeated low-resolution screens inside one output suggested the capture was undersampling, using the wrong stride, or grouping stream data incorrectly.

LCD_CAM Raw Capture

The move from polling and line bursts into LCD_CAM/raw capture was the point where the project started behaving like a real instrument. The ESP32-P4 could collect more coherent data, while the host could try many interpretations without reflashing firmware.

Core lesson: firmware should capture generic evidence. Host tools should explore interpretation: width, height, crop, byte stride, line skew, bit order, inversion, and color packing.

Color And Packing Experiments

The target probably exposes RGB-style parallel data, but "RGB666" as a connector hypothesis is not the same as a working capture mode. Increasing bit depth changed throughput, packing, and stream interpretation. Some RGB666 attempts produced the old tiling symptom again, while packed modes such as RGB332 and RGB565-style decoding became useful for live viewing.

The current boot screen is visually plausible: black text over a yellowish background. That matches the no-cartridge state well enough to use as a working baseline, but varied cartridge content is still needed before calling the color path final.

Browser Workbench

The browser is no longer just a picture viewer. It is the user-facing investigation surface for the ESP32-P4 tool. The important design decision is that live view must remain simple and reliable, while investigation tabs expose pin reads, timelines, timing capture, signal scans, exports, and target-profile metadata.

What it should preserve

  • Live monitor behavior that recovers when the console is switched off and on.
  • Profile-aware pin naming and safety status.
  • Capture settings that can be saved as named presets.
  • Artifacts that can be linked from reports.

Why it matters

A future AI-assisted workflow will need the same surfaces a human uses: live frames, pin states, signal timelines, capture manifests, decode settings, and reproducible output files.

Related docs: investigation_workbench.md and universal_signal_lab.md.

Power-Cycle Lesson

The biggest non-image lesson came from a failure mode: the GBC sometimes would not switch back on while connected. Later measurement showed that with the GBC unpowered and the ESP32-P4 powered, several bus lines sat around intermediate voltages. That strongly suggested the ESP32-P4 side could bias the target.

Software mitigations tried

  • SAFE_IDLE
  • ELECTRICAL_ISOLATE
  • Startup isolation
  • Browser Stop isolation

Decisive practical change

CLS was moved from GPIO32 to GPIO3. After that, the console could be switched off and on consistently while the live capture system was running.

Power monitor artifacts are preserved as raw.json and summary.json.

Do not lose this: GPIO32 is historical for this target. The current working baseline uses GPIO3 for CLS.

Open Technical Questions

  • What exact role does CLS play in the LCD driver timing?
  • Is the extra line/byte behavior porch-like blanking, dummy transfer, or capture framing?
  • What is the final true source color packing across varied game content?
  • Which sample edge remains stable across all connected colors?
  • Does the missing original LCD panel termination or strap behavior affect disconnected flex lines?
  • What hardware buffer or protection should be added before this becomes a repeatable lab fixture?
